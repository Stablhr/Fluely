## What Fluely is

A social content planner: plan posts across platforms, see them on a calendar, board, or table, and
edit them in place. Built on an auth boilerplate — a Next.js 16 frontend plus an Express API with
JWT auth, roles, email verification, and password reset. The planner UI is ported from
[Stablhr/Kali](https://github.com/Stablhr/Kali) into `frontend/components/kali/`.

### Architecture reality worth knowing

**Boards are server-backed; social posts are not.** The browser store (`frontend/lib/kali/store/`)
caches boards and writes through to the API with an optimistic-concurrency `revision` per board.
Social posts and connected social accounts have no backend routes. Their modules
(`lib/kali/api/social-posts.ts`, `social-accounts.ts`) still use the legacy fetch wrapper in
`lib/kali/api/client.ts`, which does nothing unless `NEXT_PUBLIC_KALI_API_URL` is set, so that data
lives only in `localStorage` and does not follow a user across browsers.

**Per-card activity is local.** Card comments, attachments (`media`), and covers come from the
server, but the per-card `activity` feed is still generated by each client and never synced
(`toCard` in `lib/kali/api/boardChildren.ts`). The board-level activity panel is server-backed.

## Next steps

Ordered by dependency, not by size.

1. **Persist social posts and accounts.** Add `SocialPost` (and social account) models, routes, and
   DTOs on the backend, move `social-posts.ts` / `social-accounts.ts` onto `httpClient`, migrate
   existing `localStorage` posts on first load (as was done for board children), then delete
   `lib/kali/api/client.ts` and the `NEXT_PUBLIC_KALI_API_URL` path.
2. **Resolve the two post editors.** `social/ComposeModal.tsx` (~700 lines, used from a card's
   social posts) and `content-planner/PostDetailPanel.tsx` (~465 lines) both create and edit a
   `SocialPost` with overlapping but different field sets. Pick one, or make the panel the shared
   core that ComposeModal composes. Easier after step 1 settles the server shape.
3. **Reconcile `/schedule` with Social Posting.** Board cards with due dates and social posts with
   scheduled dates are still two models. Either merge them or document why both exist.
4. **Add frontend tests.** The store reducer, the `boardChildren.ts` mappers, and the status/stage
   folding map in `planner-model.ts` are pure functions with branching logic and the best first
   targets. No frontend test runner is configured yet.
5. **Decide the logo situation.** The small inline logo in the auth page's left panel and the large
   overlapping wordmark both point at `fluely_logo.png`. If the intent was two distinct marks, the
   small one should point at `fluely_favicon.png`.

## Known gaps

- **Refresh-token blocklist is in memory** and resets on server restart (and per serverless
  instance on Vercel).
- **`SidebarTab` still includes `'goals'`** but no UI reaches it; the tips/goals sidebar is opened
  only on the `tips` tab.
- **No dark mode** — deliberately dropped so every route stays on the ivory canvas.
- **`frontend/Design.md` references `ContentPostCard.tsx`**, deleted in the planner rebuild. Left
  as-is because that section records a past color migration.

## Working on this repo

```bash
cd frontend
npm run dev          # port 3000
npx tsc --noEmit     # type check (no script; run directly)
npm run lint         # ESLint
npm run build        # production build

cd backend
npm run dev          # port 5000
npm test             # Jest suites
```

`frontend/.prettierrc.json` sets single quotes, no bracket spacing, and 100-column lines, and drops
semicolons under `lib/kali/` and `components/kali/`. Some older files predate it, so run prettier
only on files you are already changing to avoid whole-file diffs.

Commits follow conventional commits: `fix:`, `feat:`, `refactor:`, `chore:`, `docs:`.
